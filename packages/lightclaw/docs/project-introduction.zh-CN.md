# LightClaw 项目介绍与面试讲稿

## 简历项目描述

**LightClaw｜轻量级、可恢复、可评测的个人 Agent**

- 基于 TypeScript、`pi-agent-core` 和 OpenAI 兼容接口实现飞书/Slack Agent，支持工具调用、会话持久化、上下文压缩和频道级记忆。
- 设计长期目标状态机，将目标、进展和完成证据持久化到 JSON；实现重启恢复、最大轮次、连续失败、停滞检测和用户中止，避免 Agent 无限循环。
- 构建数据集驱动的 Agent Eval，自动检查回复、文件产物、工具错误、耗时、Token 和费用；真实评测发现并修复目标工具误调用问题，复测 2/2 用例通过、工具错误归零。
- 实现“生成候选—同集复测—严格提分后发布”的提示词优化闭环；使用非 root Docker Sandbox，限制 CPU、内存、进程、网络、Linux capabilities 和权限提升。

## 30 秒介绍

LightClaw 是我基于 pi-mono 二次开发的轻量个人 Agent。它通过统一传输层接入飞书和 Slack，底层使用 OpenAI 兼容模型，能够调用 bash 和文件工具完成真实任务。相比普通聊天机器人，我重点解决了三个工程问题：长期任务如何持久化并在重启后恢复，失败或停滞时如何熔断，以及 Agent 效果如何通过固定数据集而不是主观感觉评估。项目还包含提示词自动优化和资源受限的非 root Docker 沙箱。

## 两分钟介绍

这个项目的出发点是：聊天机器人只需要生成回答，但 Agent 会执行工具、修改文件并运行多轮，所以必须把可靠性和安全边界放到模型之外。

请求从飞书或 Slack 进入统一的 `ChatTransport`，由 `main.ts` 做频道队列和生命周期管理，再交给 `AgentRunner`。模型通过 pi 的 Agent Loop 决定是否调用工具；上下文、记忆和聊天日志分别持久化，进程重启后能够恢复。

长期任务使用独立的目标状态机，而不是只依赖对话上下文。模型必须通过工具记录进展，完成时必须提供证据。外层执行器限制最大轮次、连续失败和连续无进展次数，用户也能暂停、恢复或取消任务。

为了验证效果，我增加了 JSON 评测集和规则评分器。评测会运行真实 Agent，检查最终回复、文件是否存在、文件内容、工具错误、耗时和 Token，并输出 JSON 报告。第一次真实评测发现普通任务错误调用目标工具，修复工具描述后复测达到 2/2，工具错误从 2 个降到 0。提示词优化复用同一评测器，只有候选得分严格超过基线才保存，避免凭感觉覆盖线上提示词。

工具默认运行在 Docker 中。容器使用非 root 用户，并限制 CPU、内存、进程数、网络和 Linux capabilities。我的取舍是保持单 Agent 和基础工具，不引入重型编排框架，让每一层状态和失败路径都容易解释与测试。

## 常见追问

### 为什么不使用 LangChain？

项目目标是学习和展示 Agent 最小闭环。pi 已经提供模型协议和 Agent Loop，剩余的传输、状态、评测和安全边界用小模块实现更容易调试。复杂工作流增多时可以再引入编排层，而不是预先承担框架复杂度。

### 为什么目标状态不能只写在上下文中？

上下文会被压缩、截断，也可能因为进程退出丢失当前执行位置。独立 JSON 状态保存目标、轮次、进展版本和证据，使恢复逻辑具有确定性。

### 为什么一次 100% 不能证明 Agent 很可靠？

当前只有两个冒烟用例，而且模型输出具有随机性。它证明评测链路有效，不代表覆盖所有场景。更严格的做法是扩充任务类型、多次重复运行、划分优化集和保留集，并报告平均值与方差。

### 提示词自动优化如何防止越改越差？

当前实现不会直接覆盖系统提示词。候选必须在同一评测集上严格高于基线才写入独立文件，仍由人显式启用。下一步可增加保留集，降低对优化集过拟合的风险。

### Docker 是否绝对安全？

不是。它能限制文件可见范围、资源消耗和系统权限，但容器逃逸、挂载敏感目录和外部凭证权限仍然是风险。因此还要坚持最小挂载、最小权限凭证和必要时关闭工具网络。
